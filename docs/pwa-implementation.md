# Предложение по реализации PWA для betonicum.ru

Документ описывает архитектуру, этапы и готовый стартовый код PWA-слоя поверх
существующего WordPress-сайта. Обоснование — в [docs/ux-research.md](ux-research.md), раздел 6.

---

## 1. Подход: PWA-слой поверх WordPress, без переписывания сайта

Рассматривались три варианта:

| Вариант | Описание | Вердикт |
|---|---|---|
| **A. Готовый WP-плагин** (PWA for WP, Super Progressive Web Apps) | Установка из каталога плагинов | Быстро, но негибко: нет контроля над стратегиями кэширования, офлайн-библиотекой ТДС и push-логикой; плагины тянут лишний код |
| **B. Собственный лёгкий PWA-слой** (manifest + service worker + mu-plugin) | ~300 строк своего кода, полный контроль | ✅ **Рекомендуется.** Стартовый код готов в `/pwa` |
| C. Headless-перестройка (Next.js/Nuxt + WP REST API) | Полное переписывание фронтенда | Избыточно для текущего масштаба; имеет смысл только вместе с редизайном |

Вариант B не трогает существующие шаблоны: добавляются три статических файла в корень сайта
и один небольшой WordPress-плагин, который подключает манифест и регистрирует service worker.

---

## 2. Архитектура

```
betonicum.ru (WordPress, как есть)
│
├── /manifest.webmanifest      ← паспорт приложения (имя, иконки, цвета, shortcuts)
├── /sw.js                     ← service worker в КОРНЕ (scope = весь сайт)
├── /offline.html              ← автономная офлайн-страница
├── /pwa/icons/*.png           ← иконки 192/512 + maskable
├── /pwa/js/pwa-register.js    ← регистрация SW + кнопка «Установить приложение»
│                                + кнопка «Сохранить офлайн» на карточках/ТДС
└── wp-content/mu-plugins/betonicum-pwa.php  ← подключение всего выше + meta-теги
```

### Стратегии кэширования (реализованы в `pwa/sw.js`)

| Тип ресурса | Стратегия | Зачем |
|---|---|---|
| HTML-страницы | **Network-first** с фолбэком на кэш → `offline.html` | Контент всегда свежий, но сайт открывается и без сети |
| CSS/JS темы | **Stale-while-revalidate** | Мгновенная загрузка, тихое обновление |
| Картинки, шрифты | **Cache-first** (с лимитом записей) | Фото объектов и палитры Resalux тяжёлые и редко меняются |
| **PDF (ТДС, регламенты)** | **Cache-first + явное «Сохранить офлайн»** | Ключевой сценарий: документ, сохранённый в офисе, открывается в цеху без связи |
| Админка `/wp-admin`, `/wp-login` | не перехватывается | Безопасность и отсутствие сюрпризов у редакторов |

### Ключевая фича: «Документы офлайн»

На каждой карточке продукта рядом со ссылкой на ТДС выводится кнопка **«Сохранить офлайн»**
(скрипт `pwa-register.js` добавляет её к ссылкам с атрибутом `data-pwa-save`). Файл кладётся
в отдельный кэш `betonicum-docs`, и страница `/offline.html` показывает список всех
сохранённых документов — это и есть «полевая библиотека» подрядчика.

## 3. Этапы внедрения

### Фаза 1 — базовый PWA (1–2 недели, код в `/pwa` готов)
- [x] `manifest.webmanifest` с иконками, shortcuts («Продукция», «Объекты», «Контакты»)
- [x] Service worker: офлайн-режим, кэширование, офлайн-страница
- [x] Кнопка установки (обработка `beforeinstallprompt`) и iOS-подсказка
- [x] Кнопка «Сохранить офлайн» для PDF + библиотека сохранённых документов
- [x] WordPress mu-plugin для подключения
- [ ] Деплой файлов в корень сайта, проверка Lighthouse (цель: PWA installable, Performance 80+)

Требования: сайт на HTTPS (обязательное условие service worker), доступ к файлам сайта.

### Фаза 2 — контентные сценарии (2–4 недели)
- Калькулятор расхода материала (м² × толщина × система → кг и стоимость по запросу) —
  работает офлайн, считается на клиенте;
- Центр документации: страница со списком всех ТДС/регламентов/сертификатов с массовым
  «Скачать всё для объекта»;
- Мастер подбора системы по условиям эксплуатации (тоже офлайн-способный).

### Фаза 3 — вовлечение (4+ недели, требует бэкенда)
- Web Push (новые материалы, изменения цен, статус заявки) — через VAPID + страница
  подписки; для WP подойдёт связка с Firebase Cloud Messaging или собственный
  endpoint на `web-push` (Node) / `minishlink/web-push` (PHP);
- Личный кабинет партнёра: история заявок, повторный заказ, персональные цены;
- Background Sync: форма заявки, отправленная без сети, уходит при появлении соединения.

## 4. Деплой Фазы 1 (чек-лист)

1. Скопировать в **корень сайта** (рядом с `wp-config.php`):
   `pwa/manifest.webmanifest`, `pwa/sw.js`, `pwa/offline.html`, каталог `pwa/`.
2. Скопировать `pwa/wordpress/betonicum-pwa.php` в `wp-content/mu-plugins/`
   (каталог создать, если его нет — mu-plugins активируются автоматически).
3. Убедиться, что сервер отдаёт `manifest.webmanifest` с MIME `application/manifest+json`
   (фрагмент для nginx/apache — в комментарии внутри mu-plugin).
4. Проверить: Chrome DevTools → Application → Manifest / Service Workers;
   Lighthouse → категория PWA; установка на Android и iOS (Safari → «На экран Домой»).
5. На карточках продуктов добавить атрибут `data-pwa-save` ссылкам на ТДС-PDF.

## 5. Метрики успеха

| Метрика | Как мерить | Цель через 3 мес. |
|---|---|---|
| Установки PWA | событие `appinstalled` → Яндекс.Метрика | 5–10 % постоянных посетителей |
| Повторные визиты из standalone | `display-mode: standalone` в Метрике | рост частоты визитов партнёров |
| Скорость повторной загрузки (LCP) | CrUX / Lighthouse | < 1,5 с |
| Офлайн-сохранения документов | событие на кнопке «Сохранить офлайн» | 50+ сохранений/мес. |
| Заявки с мобильных | цели в Метрике | +15–20 % |

## 6. Риски и ограничения

- **iOS:** нет `beforeinstallprompt` и push работает только с iOS 16.4+ и только для
  установленных PWA; в `pwa-register.js` предусмотрена текстовая подсказка для Safari.
- **Кэш и редакторы:** стратегия network-first для HTML гарантирует, что правки контента
  видны сразу; версия кэша (`CACHE_VERSION` в `sw.js`) повышается при изменении статики.
- **Безопасность WP:** до деплоя обязательно закрыть находку с посторонними файлами в
  `uploads` (см. UX-исследование, п. 4.1) — service worker на скомпрометированном сайте
  закэширует и вредоносный контент.
